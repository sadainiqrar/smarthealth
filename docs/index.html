MediNova · SmartHealth

A healthcare operations platform, and the AI assistant on top of it

SmartHealth runs a fictional clinic network's day: patients and providers, bookings that confirm only when every step succeeds, visits and no-shows, cancellations that free the slot and refund the money, notifications, clinical notes and prescriptions, analytics — plus a chat assistant that answers from the clinic's own documents and books, cancels and looks things up for you, always asking before it changes anything.

Overview

Built in five weeks as a training assignment, in two parts with a prescribed stack. Part A is the core platform (FastAPI, PostgreSQL, MongoDB, Redis, Temporal, Kafka + Schema Registry, Celery + RabbitMQ, OpenTelemetry, Prometheus, Grafana, Jaeger). Part B is the GenAI layer (LangGraph, LangChain, an LLM provider — Groq, a vector database — Qdrant). Everything runs with Docker Compose.

Three rules hold the design together. (1) An appointment is confirmed only after the whole booking workflow succeeds — any failure leaves no held slot and no half-booking. (2) Everything asynchronous is idempotent: every event, job and workflow can be delivered twice and still happen once. (3) The AI model never writes: every change goes through a deterministic flow and a human "yes".

Features by role

Four fixed roles. Part A's API enforces who may do what; the assistant acts with the user's own login, so it can never do more than the user could.

🧑 Patient

  • Book, reschedule and cancel appointments; join a waitlist for a full day
  • See my appointments and my record: visit summaries, prescriptions, test orders and results
  • Upload a report (PDF) against a test order
  • Emails/SMS: confirmation, 24 h reminder, cancellation, reschedule, missed visit, refund, visit summary
  • Assistant: "do I fast before a thyroid test?", "book me with a skin doctor", "what was prescribed?"

🩺 Provider

  • My day; a brief on the next patient
  • Mark a patient seen and complete the visit — only my own appointments
  • Write, sign and amend versioned clinical notes; prescriptions and test orders are created on signing
  • Review uploaded results
  • Assistant: patient instructions drafted for approval, results to review

🗂️ Front desk

  • Register walk-in patients (a patient need not have a login)
  • Find patients, book and cancel for them, check them in
  • Manage the waitlist
  • Assistant: guided booking for a named patient, capacity, no-shows

🛠️ Admin

  • Register and update providers; deactivate one — their future appointments are cancelled and refunded
  • Analytics: bookings over time, completed visits, cancellation rate, average wait, utilisation
  • Reports written in the background (weekly/monthly operations, utilisation, engagement, a system health snapshot)
  • AI usage: tokens, estimated cost, time to first token, bookings that came from chat
  • System health: every process, the critical flows, backlogs and the assistant as ok / warn / bad with a reason, over 1, 6 or 24 hours, and the newest failures with a link to the trace
  • Send an approved message to patients; user directory

Behind every feature: an audit trail of profile and operational changes (MongoDB), and a domain event on Kafka for every change other parts of the system care about.

Why not split Part A further? Because its rules are database rules: at most one live appointment per slot (partial unique index), slot status changes together with appointment status (one transaction), no overlapping slots (exclusion constraint). Constraints do not cross a service boundary. The processes already scale independently — the Temporal worker and the Celery worker are separate containers — which covers the loads most likely to grow.

Temporal · Kafka · Celery — who does what

Three tools that all "do things later". The most likely architectural mistake in this project is using the wrong one, so each has one job.

Temporal — "run these steps, and finish"

Durable multi-step processes that must complete even if a process crashes mid-way: booking, reschedule, the visit timer, cancel follow-up, post-visit charge, provider deactivation. Every finished step is recorded; a restart resumes, never repeats.

Kafka — "this happened"

Domain facts, written in the same transaction as the change (outbox) and read by every module or service that cares, each at its own pace. Adding a reader never touches the writer.

Celery + RabbitMQ — "please do this"

Fire-and-forget jobs for exactly one worker: send this email, extract this PDF's text, and the scheduled sweeps (Beat). Retries with backoff; a dead-letter queue for what never succeeds.

The rule: if the request is the process (book, reschedule), start the workflow directly and answer 202. If the request commits a fact (cancel, deactivate, complete), write an event with it and let a consumer start the follow-up — so the follow-up can never be lost.

Kafka & events

Every change other parts care about is written as an event in the same transaction as the change (the transactional outbox). A relay publishes it to Kafka as Avro checked against Schema Registry. Each consumer group reads every event at its own pace; the consumer runtime ignores repeats and dead-letters poison.

Event vs state topics. Event topics (appointments.cancelled) keep 7 days of
  "this happened". State topics (providers.state) are compacted: the latest value per key forever, so a
  new service reads from the beginning and has the whole directory — that is how the knowledge service builds its
  own provider list without touching Part A's database.

Workflows are deterministic checklists; activities do the I/O and are idempotent. Workflow ids come

Celery jobs

  
Commands for exactly one worker, over RabbitMQ (vhost part-a). Late acknowledgement
  (a killed worker's job is redelivered), one message per worker at a time, a dead-letter queue
  notifications.dlq. Beat runs the clean-up rounds.

Tools & alternatives

  
For every tool: what we use it for, what else could do the job, why we chose ours, and when we would
  switch. Green rows are SmartHealth's choice. Much of the stack was prescribed by the assignment — where so, the
  "why" says what the tool earns here, not why it was picked.


  
API framework

  

    
OptionTrade-off

    
FastAPI (ours, prescribed)Async, typed with Pydantic, OpenAPI/Swagger for free; dependency injection carries auth, sessions and the clock into routes

    
Django + DRFBatteries included (admin, ORM, auth); heavier, sync-first; its ORM would compete with SQLAlchemy

    
FlaskMinimal; validation, async and docs are add-ons

    
Litestar, StarletteSimilar to FastAPI; smaller ecosystems

  


  
ORM and migrations

  

    
OptionTrade-off

    
SQLAlchemy 2 (async) + Alembic (ours)Full SQL power when needed (the slot claim is a raw conditional UPDATE), constraints and indexes declared in models, autogenerated migrations checked by alembic check

    
SQLModelSQLAlchemy + Pydantic in one class; less control over advanced constraints

    
Tortoise, PiccoloAsync-first, simpler; smaller ecosystems, weaker migration tooling

    
Raw SQL (asyncpg)Fastest, most explicit; no model metadata to generate migrations or docs from

  


  
Transactional database

  

    
OptionTrade-off

    
PostgreSQL (ours, prescribed)Exclusion constraints, partial unique indexes, row locks, SKIP LOCKED for the relay, advisory locks for patient overlap — the invariants live here

    
MySQL / MariaDBNo exclusion constraints or partial indexes — the double-booking rules would move into code

    
CockroachDB / SpannerDistributed SQL for global scale; overkill for one clinic network

  


  
Audit store (the "NoSQL database")

  

    
OptionTrade-off

    
MongoDB (ours)Append-only documents with free-form before/after snapshots; the audit trail never constrains the transactional schema

    
A Postgres audit table (JSONB)Could share the transaction (atomic with the change); the assignment asks for a NoSQL store, and we accept the non-atomic write (PRD R-1)

    
Event sourcing / Kafka as the logFull history by construction; far more machinery

    
DynamoDB, CassandraManaged/massive scale; not needed

  


  
Cache, sessions, rate limits

  

    
OptionTrade-off

    
Redis (ours, prescribed)Server-side sessions (revocable JWTs), login throttling, per-user booking limits, per-patient notification throttles; Redis Streams for the assistant's resumable turns

    
MemcachedPlain cache; no data structures, no streams

    
Postgres tablesOne less system; slower for hot counters and expiry

    
Stateless JWT onlyNo server state — but no way to log a user out or revoke a token before it expires

  


  
Durable workflows

  

    
OptionTrade-off

    
Temporal (ours, prescribed)Each step recorded; crash-safe resume; timers that last days (no-show, reminders); child workflows (waitlist bookings); workflow ids as dedupe

    
Hand-rolled saga (status column + cron)No new system; you rebuild retries, timers, state and visibility yourself

    
Celery chains/chordsAlready in the stack; no durable state between steps — a crash mid-chain leaves you guessing

    
AWS Step Functions, Azure Durable FunctionsManaged; cloud lock-in, JSON/YAML state machines

    
Airflow, Prefect, DagsterData-pipeline schedulers; not built for per-request business processes

    
Camunda / ZeebeBPMN-modelled; heavier, Java-centric

  


  
Event streaming

  

    
OptionTrade-off

    
Kafka + Schema Registry (Avro) (ours, prescribed)Many independent consumer groups, ordered per key, replayable, compacted state topics; schemas checked for compatibility at deploy

    
RabbitMQ topic exchangesFan-out works, but messages are gone once consumed — no replay, no compacted state

    
Redis StreamsConsumer groups and replay in a store we have; weaker durability and tooling at scale

    
NATS JetStream, PulsarLighter (NATS) or multi-tenant (Pulsar); smaller ecosystems here

    
Postgres LISTEN/NOTIFYNo new system; no persistence, no consumer groups

  

  

    
SerialisationTrade-off

    
Avro + Schema Registry (ours)Compact, schema-enforced, compatibility rule BACKWARD_TRANSITIVE refuses a breaking change at deploy

    
JSONHuman-readable; no enforced contract — a renamed field breaks consumers silently

    
ProtobufAlso schema-first (we use it for gRPC); Avro is Kafka's most common pairing with Schema Registry

  


  
Background jobs

  

    
OptionTrade-off

    
Celery + RabbitMQ (ours, prescribed)Retries, late acks, routing, dead-letter queues and Beat schedules as configuration

    
RQ, Dramatiq, Huey, arqSimpler; fewer features (arq is async-native)

    
Temporal activities for everythingDurable, but heavyweight for "send one email"

    
Cloud queues (SQS + Lambda)Managed; lock-in

  


  
Observability

  

    
OptionTrade-off

    
OpenTelemetry → Collector → Jaeger + Prometheus → Grafana (ours, prescribed)Vendor-neutral instrumentation; the collector decides where data goes, so swapping a backend is a config change

    
Grafana Tempo / Loki / MimirSame Grafana, cheaper object-storage backends; drop-in behind the collector

    
Datadog, New Relic, HoneycombManaged, polished; per-host or per-event cost, data leaves your network

    
ELK / OpenSearchStrong log search; heavier to run

    
Langfuse, LangSmith, Phoenix (LLM-specific)Nice prompt/response views; we keep one stack and don't ship conversation text to a third party

  


  
Admin health view

  

    
OptionTrade-off

    
An in-app page over Prometheus + Jaeger (ours, a Part A monitoring module)Plain statuses with a reason, behind the normal admin login; the same endpoints feed the assistant's report; no new image. The API must know PromQL and Jaeger's UI query API (pinned to 1.62)

    
Embed Grafana panelsNo new code; still graphs for engineers, behind a second login, with no status or reason

    
A separate ops serviceClean separation; a sixth image and chart on an 8 GB server for two read-only endpoints

    
The browser queries Prometheus and Jaeger directlyNo backend change; PromQL in the client, a second login, and nothing the assistant could call with the admin's token

  


  
Service-to-service and the browser edge

On AWS

  
The same umbrella chart runs on one private k3s server in ap-southeast-2, built by Terraform and kept equal to git by Argo CD. A reviewer opens one CloudFront address; the owner starts it before a review and it stops itself after 3 hours (README, "Deploying to AWS"; ARCHITECTURE section 8; decisions D-42 to D-54).

  
Deployed and verified on 2026-11-17: d2xy34d2kn7e5f.cloudfront.net — up only while the owner has started it for a review. Through CloudFront: the API, a demo login, the assistant's streamed answer with citations over gRPC-Web, the seven tool paths (401 without the login, 200 with it), assets cached at the edge and the API not. From inside the server: Argo CD Synced / Healthy, every pod running, a booking confirmed in 2 seconds and cancelled with both emails delivered, and traces from eight services in Jaeger.

  
What the first deploy found, and fixed
    
    
  • Git Bash rewrote SSM names. /smarthealth/jwt-private-key reached aws.exe as a Windows path; scripts/aws_lib.sh now turns that off for aws calls only.
    • 
    
  • Saved plans were not ignored. A plan file can hold secret values; *.tfplan and tfplan are git-ignored.
    • 
    
  • An all-digit tag became a number. The release 3244061 rendered as smarthealth-core:3.244061e+06 (InvalidImageName on five pods); set_release.py quotes the tag, and a meta-test covers it.
    • 
    
  • GHCR's first push of a new package answered denied once after the layers uploaded; a retry succeeded. New packages start private.
    • 
    
  • CloudFront needed account verification. New AWS accounts are held until AWS Support verifies them (R-35, closed the same day).
    • 
    
  • Four script faults found by testing before CloudFront existed (a start script that needed the URL, a 100-second SSM wait, an exec of a shell function, WSL's bash found before Git Bash), each pinned by a meta-test.
    •

  repository: one requires a validated test case when core code changes, the other requires the documentation
  (including this site) to be reviewed when the application changes.







  
Decisions & open items

  

    
A patient is not a user
Logins and patient records are separate; front desk registers walk-ins with no credentials.

    
Slots are pre-generated rows
Booking is a conditional UPDATE; zero rows is the conflict. No availability generator — slots are seeded.

    
A visit is not an appointment
Appointment = the booking; visit = what happened. A no-show is an appointment with no visit.

    
The outbox, not "publish after commit"
An event is written in the change's own transaction, so it cannot be lost if Kafka or the process dies.

    
The model never writes
Two read-only tools; every change is a deterministic flow plus a confirmation.

    
A private server, a public edge
On AWS the server has no public address and no SSH; CloudFront reaches it over AWS's network, Argo CD pulls from git, secrets come from SSM.

    
No shared stores
Part B owns its data, reads Part A only through its API and events, verifies tokens with JWKS.
